# FISC01 — Perfiles de facturación de pacientes

`billing_patient_profiles` pertenece a la relación médico–paciente, no a la identidad global del paciente. La API usa únicamente el médico de la sesión y exige una relación activa en `patients_doctor_links` y un paciente activo. Los identificadores de perfil se consultan siempre junto con médico y paciente. No se delega el acceso mediante el permiso `billing` de Operadores de Agenda.

La migración `db/2026_09_16_01_create_patient_billing_profiles.sql` se debe aplicar **sólo después** de inspeccionar el esquema físico y descartar una autoridad fiscal preexistente. FISC01 no contiene tablas de facturas ni almacenamiento de XML/PDF. El archivo lógico conserva perfiles archivados para futuras referencias y la clave única generada impide dos predeterminados activos por médico y paciente. Las transacciones bloquean la relación médico–paciente antes de cambiar el predeterminado.

El archivo `catalog/sat-cfdi-4-20260903.json` contiene todas las filas de `c_RegimenFiscal` (19) y `c_UsoCFDI` (24) extraídas de [Catálogo CFDI 4.0 del SAT](http://omawww.sat.gob.mx/tramitesyservicios/Paginas/documentos/catCFDI_V_4_20260903.xls), publicado el **03-09-2026** y verificado el **16-09-2026**. El JSON registra el SHA-256 del XLS, tipo de persona, fechas de vigencia y regímenes permitidos para cada uso. La validación comprueba claves, vigencia y compatibilidad; no verifica la inscripción efectiva del RFC ante el SAT.

Ruta: `/api/billing/patient-profiles.php`. `GET?action=catalog` entrega el catálogo y token CSRF; `GET?action=search&q=...` reutiliza `PatientsRepository::searchPatientsByDoctorId`; `GET?patient_id=...` lista perfiles activos. `POST` crea, `PUT` edita, `POST` con `action=set_default` cambia el predeterminado y `DELETE` archiva. Las escrituras requieren `X-Billing-Profiles-CSRF`. Las respuestas llevan `Cache-Control: private, no-store`; no se registran valores fiscales en logs.

## FISC02A — Archivo de facturas históricas

`db/2026_09_16_02_create_billing_invoices.sql` crea `billing_invoices` después de FISC01 y añade una clave compuesta al perfil de facturación. La factura conserva relación obligatoria médico–paciente y un vínculo opcional al perfil que debe pertenecer a la misma relación. El perfil es sólo procedencia: nombre, RFC, CP, régimen y uso CFDI del receptor se copian del XML en la factura y ningún cambio posterior al perfil los recalcula. El API no ofrece edición ni eliminación de facturas. Las claves únicas `(doctor_id, cfdi_uuid)` y `(doctor_id, xml_sha256)` impiden duplicados dentro del alcance médico. `source_type` admite `HISTORICAL_IMPORT` y reserva `PAC_ISSUED` para una fase posterior; una importación inicia con `status=UNKNOWN` porque el XML no prueba vigencia actual ante el SAT.

`api/billing/invoices.php` ofrece `GET?action=list` para la lista básica, `POST` JSON `action=search` para filtros de paciente, receptor, RFC, UUID, fechas y estado, `GET?action=detail`, `GET?action=download&kind=xml|pdf`, `POST action=preview` y `POST action=import`. RFC y nombre fiscal no se envían en URL para evitar su aparición en registros de acceso. Las solicitudes POST exigen sesión médica y token `X-Billing-Invoices-CSRF`; la importación exige además paciente activo y confirmación explícita de los SHA-256 vistos en la vista previa. La lista y el detalle no exponen rutas ni claves privadas. La descarga vuelve a comprobar médico, paciente, factura activa, clave esperada y hash del objeto; entrega `attachment` con nombre seguro. No hay URL pública directa de XML/PDF.

El importador admite exclusivamente CFDI 4.0 de ingreso con Timbre Fiscal Digital 1.1 y UUID; XML obligatorio y PDF opcional, cada uno con límite de 5 MiB. Rechaza DTD/entidades, red XML externa, documentos no CFDI y PDF sin firma y fin reconocibles. El XML proporciona los metadatos y el receptor histórico; el PDF sólo es una representación adjunta. `InvoiceDocumentStorage` usa `MXMED_PRIVATE_BILLING_ROOT` o, por defecto, `$HOME/.local/share/mxmed/private-billing`, siempre fuera del repositorio y del document root; crea directorios `0700` y objetos `0600` sin sobrescritura. La importación bloquea la relación médico–paciente, registra los documentos de forma inmutable y revierte los objetos recién creados si falla la transacción. No amplía el espacio de claves de medios públicos.

La UI bajo **Facturación → Pacientes** conserva el buscador canónico de FISC01 y añade **Datos de facturación | Facturas** al seleccionar paciente. **Listar Facturas** consulta el mismo archivo para el médico y reemplaza las filas de ejemplo. **Facturas Canceladas** permanece informativa hasta contar con una autoridad fiscal de cancelación. **Crear Factura / Timbrar** sigue deshabilitado: FISC02A no emite CFDI ni integra PAC.

La migración se aplicó y verificó en la base local de QA el 16-09-2026 después de confirmar que no existía otra autoridad de facturas. Para otros entornos se requiere el mismo preflight físico; esta migración no debe ejecutarse dos veces. `tests/InvoiceArchiveTest.php` cubre parser, XXE, PDF y almacenamiento. Las pruebas de API y navegador usan únicamente CFDI sintéticos y eliminan sus filas y objetos al terminar.
