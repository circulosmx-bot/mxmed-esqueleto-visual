# LON03A longitudinal antecedent authority

This is an additive backend foundation. It does not populate or edit LON01/LON02, M7, or `clinical_record_entries`. There is no UI writer. `MXMED_LON03A_WRITE_ENABLED=1` is required for mutation; it is unset/off by default. The existing clinical write-window still admits or rejects each HTTP writer.

Apply `db/migrations/2026_09_21_06_longitudinal_antecedents.sql` only after the patient and M7 encounter tables exist. The script creates four current-state authorities, an append-only clinical audit table and a separate command-idempotency ledger. No legacy backfill runs. `clinical_patient_allergy_reviews` is the canonical name for the separate allergy review authority.

`GET /api/clinical/index.php/patients/{patient_id}/longitudinal/{resource}` reads one of `antecedents`, `antecedent-reviews`, `allergies`, or `allergy-reviews`. Append `/{id}` to read an item, `/history` or `/{id}/history` to read ordered audit events. The antecedent list returns `knowledge_state_by_category`; the allergy list returns `knowledge_state`. Missing review rows produce `UNKNOWN`, even when the list is empty. Adding or changing a fact/allergy invalidates an earlier review to `NEEDS_REVIEW`; it never silently confirms a clinical negative.

`POST` to the collection creates a record. `PATCH` to `/{id}` updates a record. Each command requires an authenticated doctor session, active doctor–patient link, `Idempotency-Key` header and canonical JSON. PATCH also requires `expected_version` and a nonempty `reason`. Review creation/update is explicit; `CONFIRMED_NONE` conflicts with current rows. The command service serializes within the active doctor–patient link, compares versions, writes state and its clinical audit event in one transaction, then commits the idempotency result. There is no DELETE route. MySQL triggers also reject deletion of current records and update/deletion of audit events.

Supported categories are `PERSONAL_PATHOLOGICAL`, `PERSONAL_NON_PATHOLOGICAL`, `SURGICAL`, `FAMILY`, `HABITS`, `VACCINATION`, `GYNECOLOGICAL`, and `OTHER`. Antecedent facts use `CURRENT` or `INACTIVE`; allergies use those states plus `REPORTED` or `CLINICIAN_REVIEWED` validation. A document source is accepted only if it is tied to an encounter of the same doctor and patient. Encounter and section sources receive the same check. `LEGACY_IMPORTED_CONFIRMED` and `EXTERNAL_SOURCE` are reserved provenance classes, currently rejected by the service because existing legacy/external records cannot establish a doctor-attributable source. A later authorization must define their source authority before enabling them.

Run `bash modules/clinical/qa/lon03a_disposable_gate.sh` for a fresh, random disposable MySQL database. The gate applies the migration twice, checks schema constraints, exercises repository semantics and drops the database on exit. Never point this gate at working `mxmed`.
